* How to read this document

This is a synthesis, not four abstracts stapled together. The four papers
were published over eleven years and the vocabulary, the framing, and even
the name of the language changed along the way. Where the papers disagree,
this document follows the *most recent* formulation (Onward! '24), and every
such resolution is marked explicitly with a =CONFLICT= block so you can
trace what was overridden and why.

Explanations follow the ADEPT sequence wherever a concept is introduced:
**A**nalogy first, then a **D**iagram, then a concrete **E**xample, then a
**P**lain-English restatement, and only then the **T**echnical definition.
The papers themselves mostly run this order backwards — definition first,
motivation later — which is exactly why re-reading them cold is hard.
Code listings and diagrams are reproduced from the papers (diagrams
redrawn as ASCII with figure references); the connecting prose is new.

The reading order below is *conceptual*, not chronological:

* Part 0 — The Big Idea in one page

** Analogy

A city does not run on one kind of connection. It has roads, water pipes,
power lines, mail, and radio. Each is optimized for what it carries, and
nobody proposes delivering water by mail truck. Mainstream programming
languages are cities with only roads: the procedure call. Everything else —
storage, streams, events, constraints — must be delivered by truck, i.e.,
simulated with procedure calls, and the simulation code (the "glue") ends
up dominating and obscuring the system.

** Diagram

The one picture that organizes all four papers (Beyond Procedure Calls,
Figure 1):

#+BEGIN_EXAMPLE
  Program A   ──── HTTP ────   Program B
  Object  A   ─── Message ───  Object  B
  Filter  A   ──── Pipe ─────  Filter  B
  Procedure A ──── Call ─────  Procedure B
  ─────────────────────────────────────────
  Component A ── CONNECTOR ──  Component B     (the generalization)
#+END_EXAMPLE

Boxes are *components* (loci of computation and storage). Arrows are
*connectors* (the glue that mediates communication). Architecture is
determined by the connectors, not the boxes.

** Example

The same working system, expressed three ways (all from the papers):

#+BEGIN_SRC smalltalk
"Serve every file in $HOME over HTTP on port 8080 — SC Fig. 25"
server := ref:file:{env:HOME} -> scheme:file -> SchemeHTTPServer port:8080.
server start.

"Say Hello World to the web — BPC Listing 44"
#HTTPServer{ port: 8081 } → #MPWDictStore{ hello: 'World' }.

"Keep one directory mirrored into another, forever — BPC Listing 41"
target |= source.
#+END_SRC

No callbacks, no framework annotations, no route tables. The program text
*is* the architecture diagram, read left to right.

** Plain English

Weiher's program across the four papers is a single claim unfolding:

1. /2013:/ Names should be polymorphic, not just operations. An identifier
   that looks like a URI can point to a variable, a file, or a web
   resource, and clients cannot tell the difference.
2. /2019:/ Once names and a four-verb storage interface are separated,
   you can build *generic intermediaries* — caches, loggers, mappers —
   that snap together like HTTP proxies, but in-process and at
   procedure-call speed.
3. /2020:/ This is not a storage trick. It is one instance of a general
   disease: call/return is our only abstraction mechanism, and most modern
   systems (UIs, sync, persistence, pipelines) are not call/return-shaped.
4. /2024:/ Therefore: take the connector taxonomy from software
   architecture research, make *each connector type polymorphic* via a
   metaobject protocol, give the frequent ones surface syntax, and let one
   designator (=→=) connect anything to anything compatible. That is
   Architecture-Oriented Programming.

** Technical definition

*Architecture-Oriented Programming (AOP, Weiher's sense — not
aspect-oriented programming):* a programming model in which the connector
types identified by software-architecture research (procedure call, data
access, stream, event, distributor/naming, linkage, adaptor, arbitrator)
are first-class, *polymorphic* language concepts backed by a metaobject
protocol, so that architectural patterns are expressed directly in the
implementation rather than encoded indirectly through procedural glue or
maintained in a separate architectural description. A language is
/architecturally polymorphic/ with respect to a connector type if it can
directly express several (ideally all) variants of that type behind one
surface syntax; mainstream languages are /architecturally monomorphic/ —
one variant per supported type, usually just synchronous local calls and
direct variable access.

* Part 1 — The Gentle Tyranny of call/return (Programming '20)

This is the manifesto paper. It supplies the *why* for everything else, so
even though it postdates Storage Combinators, read it first.

** Analogy

Call/return is a tyranny that rules /gently/: it never forbids you from
building a UI binding, a cache, or a pipeline. It just makes every one of
them a simulation — close enough to the real thing that pointing out the
difference feels like splitting hairs, costly enough that the glue
eventually swallows the program. A tyrant who lets you do anything, as
long as you do it his way, is still a tyrant.

** The core observation

All three mainstream "paradigms" are the same connector wearing different
hats (Gentle Tyranny, Table 1):

| Paradigm        | Syntax  | Side effects            |
|-----------------+---------+-------------------------|
| Imperative      | =f(x)=  | discouraged             |
| Functional      | =f(x)=  | disallowed              |
| Object-oriented | =x.f()= | discouraged / contained |

All are mechanisms for /computing a result and terminating/. But — citing
Feynman ("computers... primarily are filing systems"), Guy Steele
("Ongoing behavior, not completion, is now of primary interest"), and
Black's Infopipes ("information exchange has replaced computation") — most
modern programs are about *storage, communication, and ongoing
relationships*, with computation incidental. Using the computation
mechanism as the sole abstraction mechanism produces unresolvable
architectural mismatch. Wheeler saw the dual role of subroutines in 1952:
evaluation of functions vs. organization of processes. The second use is
the strained one.

** Example — the temperature converter, death by a thousand setters

The paper's running example: a Celsius/Fahrenheit converter with UI and
persistence. In call/return style (Objective-S syntax), the *model* is
four clean methods. Then reality arrives:

Connecting the UI forces the setters to know about text fields
(GT Fig. 3, abridged):

#+BEGIN_SRC smalltalk
- f:degreesF {
    self c:(degreesF - 32) / 1.8.
    ivar:ui/celsiusTextField/intValue := self c.
}
- c:newValue {
    ivar:c := newValue.
    ivar:ui/fahrenheitTextField/intValue := self f.
}
#+END_SRC

Avoiding a redundant UI update forces a =basicC:= / =c:= split
(GT Fig. 4). Persistence adds a defaults write inside =basicC:=
(GT Fig. 5/6). Adding Kelvin multiplies every setter's UI-update burden
(GT Fig. 7) until the design collapses into a centralized =-updateUI=
(GT Fig. 8) — which reintroduces the redundant updates the earlier
contortions existed to avoid.

The punchline: none of this complexity is in the domain. It is
architectural embellishment — moving data between locations to keep
model, UI, and persistence synchronized — expressed through methods that
"perform an action and then terminate."

** The same program under dataflow constraints

With constraint connectors (=|== one-way, ==|== bidirectional), each
requirement is *purely additive*. The complete application (GT Fig. 13):

#+BEGIN_SRC smalltalk
ivar:ui/celsiusTextField/intValue    =|= ivar:c.
ivar:ui/fahrenheitTextField/intValue =|= ivar:f.
ivar:ui/kelvinTextField/intValue     =|= ivar:k.

ivar:f |= (9.0/5.0) * ivar:c + 32 .
ivar:c |= (ivar:f - 32) * (5.0/9.0).
ivar:k |= ivar:c + 273.15.
ivar:c |= ivar:k - 273.15.

ivar:c := defaults:celsius.
defaults:celsius |= ivar:c.
#+END_SRC

The whole program is the concatenation of its increments; no earlier line
was ever edited. Note that persistence became legal on the /left-hand
side/ of a constraint only because =defaults:celsius= is a Polymorphic
Identifier — a name, not a method pair. This is the load-bearing joint
between the 2020 paper and the 2013 paper.

The paper then abstracts the whole application into pseudo-architecture
(GT Fig. 15 — pseudo-code, the grouping construct did not exist yet):

#+BEGIN_EXAMPLE
ui =|= memory-model.
memory-model := persistence.
persistence |= memory-model.
#+END_EXAMPLE

** Why bindings and Java Streams don't count

Two demolitions worth keeping at hand for the thesis's related-work
defenses:

- /Cocoa bindings/ (GT Fig. 14): =[celsiusField bind:@"value"
  toObject:model withKeyPath:@"celsius" options:nil]= *sets up* the
  binding as a side effect; no line of code *is* the binding. Debuggers
  have nothing to point at. Weiher connects this to Dijkstra's goto
  argument: shorten the gap between the static program and the dynamic
  process. Constraints are to callbacks what structured control flow was
  to goto.
- /Java Streams/ (GT Fig. 23): the fluent chain *looks* like a pipeline
  but the chained calls construct filter objects; they process nothing.
  The pipeline shape is simulated through an indirection layer, extending
  the filter set is a framework-implementer task, and custom processing
  gets trapped in anonymous lambdas instead of named, reusable
  components. "The differences are not small, just subtle" — that is the
  gentleness of the tyranny.

** Technical takeaways

- Thesis of the paper: neither extend nor replace call/return —
  *generalize* it, the way general relativity contains Newtonian
  mechanics as a special case.
- The "connect and run" idiom =(stdin -> toupper -> rawstdout) run=
  is proposed as the generalization of apply/eval.
- Styles demonstrated: constraint connectors, in-process REST / storage
  combinators, pipes and filters — each validated in real systems first
  as frameworks, then linguistically integrated.

* Part 2 — Polymorphic Identifiers (DLS '13)

The oldest paper, and the foundation stone: it establishes the *naming
connector*. Everything later depends on its central separation — the
identifier names a location; the operation is specified elsewhere.

** Analogy

In OO, every drawer in every cabinet has its own custom key-and-motor
pair: =name= / =setName:=, =age= / =setAge:=. If you want to add a
security camera (logging), a copy of the cabinet in another building
(caching), or move the cabinet to the cloud, you must re-machine every
key. A URI, by contrast, is a *street address*: one universal addressing
scheme, four universal operations (GET/PUT/PATCH/DELETE), and any courier,
customs office, or forwarding service can handle any address without
knowing what lives there.

** The problem: the Uniform Access Principle unravels

Meyer's UAP demands access to state be indistinguishable from access to
computation. Languages honor it — but *only for one store*: instance
variables. The paper's opening exhibit (PI Listing 1), retrieving "name"
from five different stores in Objective-C:

#+BEGIN_SRC objc
name;                                              // local variable
[person name];                                     // message
[person objectForKey:@"name"];                     // dictionary
[NSString stringWithContentsOfFile:@"name"];       // file
[[NSData dataWithContentsOfURL:[NSURL URLWithString:
    @"http://www.person.com/name"]] stringValue];  // web
#+END_SRC

Five stores, five incompatible syntaxes. The paper then proves by
exhaustion (sections 2.1–2.3) that every conventional repair is bad:

1. /Make objects dictionary-compatible/ (PI Listing 5): a hand-written
   =objectForKey:= if-ladder per class — boilerplate, an order of
   magnitude slower than native access, and it abandons the language's
   own access syntax. Punishes object modeling.
2. /Make dictionaries object-compatible/ (PI Listing 6): cover-method
   pairs for *every attribute*. The storage concern smears across the
   entire codebase.
3. /forwardInvocation: trickery/ (PI Listing 7): string-mangles selector
   names into keys at ~2 µs per access — three orders of magnitude slower
   than a message send, and fragile.

So practitioners choose option 4: live with non-uniform access. The root
cause, stated precisely in §2.4: a message like =setName:= *fuses* the
L-value (=name=) with the operation (=set=). Language UAP machinery
un-fuses them only for instance-variable storage and direct access.

** The solution: three parts

#+BEGIN_EXAMPLE
   identifier ──▶ scheme-handler ──▶ reference ──▶ L-value
   (URI text)      (manages one         (Strachey        (the storage
                    store; maps          Load-Update      location)
                    names to refs)       Pair, reified)
#+END_EXAMPLE

1. *Polymorphic Identifiers* are URIs in the language: =scheme:path=.
   Valid PIs (PI Listing 13):
   #+BEGIN_SRC smalltalk
   person
   name
   var:person/name
   var:person/{attribute}
   file://tmp/button.png
   http://www.example.com/button.png
   file:{env:HOME}/rfcs/{rfcName}
   #+END_SRC
   Note URI templates (={...}=) for parameterized identifiers, and =/= as
   the path separator.
2. *References* reify the Load-Update Pair for one L-value. The default
   in-memory reference negotiates three access modes at *binding time* —
   offset, message, keyed (PI Listing 14, abridged):
   #+BEGIN_SRC objc
   -value {
       if ( offset >= 0 )       return ((id*)target)[offset];
       else if ( getSelector )  return [target perform:getSelector];
       else                     return [target objectForKey:attributeName];
   }
   #+END_SRC
   Binding separated from evaluation is the performance trick: JIT-like
   inlining without runtime code generation. References also carry
   store-specific extras: assignment is delegated to the reference (so
   file-to-file copy can become a symlink, web-to-file can stream),
   references can list children (generic browsing/export).
3. *Scheme-handlers* each manage one store and translate identifiers to
   references. Schemes are late-bound through the =scheme:= meta-scheme:
   #+BEGIN_SRC smalltalk
   scheme:http := URLSchemeResolver new.
   #+END_SRC
   Crucially (RESTLY cares): a scheme names a /namespace partition/, not a
   protocol and not a specific store — users can rebind =http:= to
   anything.

** Uniformity payoff

#+BEGIN_SRC smalltalk
name := var:person/name.       "object OR dictionary behind it — same code"
var:person/name := newName.

file:rfc1738 := http://datatracker.ietf.org/doc/rfc1738.   "download"
#+END_SRC

In-memory stores are schemes too: =ivar:=, =local:=, =thread:=,
=global:=, =class:=, with the composite =var:= scheme doing prioritized
sequential lookup — the ordinary identifier-resolution rules of a
programming language, *reconstructed from user-level combinators*. The
default scheme is bound to =var:=, so bare =greeting= is sugar for
=var:greeting=.

Composite scheme-handlers (§3.3.2) are storage combinators before the
name existed: relative schemes (prefix mapping), filter schemes (data
mapping — e.g., PNG bytes to image objects), sequential schemes, caching
schemes. PI Figure 1, redrawn — an =http:= handler with two cache layers:

#+BEGIN_EXAMPLE
  Web Client
      │
      ▼
  memcache (cache) ──▶ memory            [primitive]
      │
      ▼
  filecache (cache) ──▶ tempdir (rel) ──▶ file   [primitive]
      │
      ▼
  rawhttp (http)                          [primitive]
#+END_EXAMPLE

** Performance (PI Table 3, ns per access)

| Storage    | Keyed | Message |  PI  | PI/Offset | forwardInvocation |
|------------+-------+---------+------+-----------+-------------------|
| Object     |  58.7 |    2.50 | 3.11 |      2.22 |              2.48 |
| Dictionary |  24.2 |    26.2 | 25.9 |      29.3 |              2051 |

PI/Offset *beats a native message send* (2.22 vs 2.50 ns) while remaining
fully substitutable — the uniform-access tax is negative once binding is
separated from evaluation. The only catastrophic row is the
forwardInvocation hack the paper exists to kill.

** Technical takeaways

- The UAP is achievable for arbitrary stores, parameterized access, and
  external resources — but only by making /identifiers/ polymorphic, not
  by making more things look like messages.
- Self/Newspeak took the opposite route (everything is a message) and hit
  exactly the L-value problem: Load and Update become separate
  identifiers related only by convention ("a complexity that bothers us
  to this day" — Ungar & Smith).
- REST inverts the OO assumption: on the Web, /identifiers/ are the
  interface and messaging is the hidden implementation detail.

CONFLICT (resolved, favoring 2019/2024): the 2013 paper's vocabulary is
"scheme-handler" and "composite scheme-handler". From 2019 on these are
"store" and "storage combinator", and the reference protocol is fixed as
{ pathComponents, path, scheme } (SC Fig. 2). Use the later vocabulary;
reserve "scheme handler" for the binding of a store to a scheme name —
i.e., the factory role, exactly as in the RESTLY =restly_schemes= ruling.
#+END_QUOTE

* Part 3 — Storage Combinators (Onward! '19)

The central paper for RESTLY — the one whose open future-work sentence the
thesis answers. It takes the naming machinery of Part 2 and builds the
*data-access connector* into a plug-composable component system.

** Analogy

On the Web you can drop a Squid or Varnish cache between any client and
any server without either of them knowing or caring — the cache speaks
GET/PUT to both sides. In-process, caches exist everywhere (Apache
modules, nginx modules, ORMs) and *none are interchangeable*, because
each is welded to its host's procedural interface. Storage combinators
are the answer to: what would in-process components have to look like for
the Squid trick to work between ordinary objects?

The theoretical warrant is Fielding's own evaluation of HTTP: requests
directed to resources through a generic interface with standard semantics
can be interpreted by intermediaries almost as well as by the origin —
and, Weiher observes, *nothing in that sentence requires distribution*.

** In-Process REST: location / operation / resolver

The load-bearing separation (SC Table 1):

|           | OO        | In-Process REST  | HTTP         |
|-----------+-----------+------------------+--------------|
| location  | (fused    | reference        | URI          |
| operation |  into the | Storage protocol | HTTP methods |
| resolver  |  message) | store            | HTTP server  |

OO fuses location and operation into the message, "thereby limiting what
an intermediary can do." Un-fuse them and generic intermediaries become
possible.

The three pieces:

*Reference protocol* (SC Fig. 2):
#+BEGIN_SRC smalltalk
protocol Reference {
    -<Array>pathComponents.
    -<String>path.
    -<String>scheme.
}
#+END_SRC

*Storage protocol* (SC Fig. 3 — identical in GT Fig. 16 and BPC Listing 2;
this is the most stable artifact in the corpus):
#+BEGIN_SRC smalltalk
protocol Storage {
    -at:ref.
    -<void>at:ref put:object.
    -<void>at:ref merge:object
    -<void>deleteAt:ref;
}
#+END_SRC

*Store*: any object implementing Storage. "There is no requirement for a
store to actually store data, it can just as easily compute it" — the
HTTP-server property, in-process.

The full operation-equivalence table (SC Table 2):

| Store                   | HTTP              | L-Values      | Smalltalk dict      | Java In-Proc REST | Java accessor          |
|-------------------------+-------------------+---------------+---------------------+-------------------+------------------------|
| =store at:ref.=         | GET <uri>         | Load          | =dict at:key.=      | =nodeForUri(ref)= | =obj.getAttribute()=   |
| =store at:ref put:d.=   | PUT <uri> <d>     | Update <d>    | =dict at:key put:d.=| —                 | =obj.setAttribute(d)=  |
| =store at:ref merge:d.= | PATCH <uri> <d>   | —             | —                   | —                 | —                      |
| =store deleteAt:ref.=   | DELETE <uri>      | —             | =dict deleteAt:key.=| —                 | —                      |

Note what the table quietly asserts: the Storage protocol *is* the
dictionary protocol plus merge — the HASH_TABLE analogy at the heart of
RESTLY is Weiher's own Table 2, columns 1 and 4.

The ancestral Java form from the BBC system (SC Fig. 1):
#+BEGIN_SRC java
public SiteMapNode nodeForUri(String path) {
    return root().subobjectForPath(path);
}
// ...
node = nodeForUri("football/premiereLeague");
#+END_SRC

** Using stores — four ways to say the same thing

#+BEGIN_SRC smalltalk
"Via API, dictionary-backed (SC Fig. 4)"
store := DictStore store.
ref := store referenceForPath:'hello'.
store at:ref put:'world'.
store at:ref.                       "→ 'world'"

"A raw Smalltalk dictionary, for comparison (SC Fig. 5)"
dict := Dictionary new.
dict at:'hello' put:'world'.

"Via API, disk-backed (SC Fig. 6) — one token changed"
store := DiskStore store.

"Via Polymorphic Identifiers (SC Figs. 7–8)"
scheme:dict := DictStore store.
dict:hello := 'world'.
dict:hello.                         "→ 'world'"

file:hello := 'world'.              "pre-bound file scheme"
file:hello.
#+END_SRC

The dict/store similarity is deliberate: keep the ergonomics of "just use
a dictionary" without marrying the implementation. This is exactly the
Wunderlist origin story below. Pre-built simple stores: dict, disk,
=http/https/ftp=, =env=, =var=, key-value and SQLite databases, windows,
AppleScript.

** The combinator concept

#+BEGIN_EXAMPLE
  a store:                 ┌───────┐
             Storage ──▶  │ store │
                          └───────┘

  a storage combinator:    ┌────────────┐
             Storage ──▶   │ combinator │ ──▶ Storage [1..n]
                           └────────────┘
#+END_EXAMPLE

(SC Figs. 9–10.) A storage combinator *provides* the Storage protocol
upward and *consumes* it downward. Because interface-in equals
interface-out, they compose like Unix filters and are closed under
composition. That symmetry is the entire mechanism.

The catalog's class hierarchy (SC Fig. 13; combinators in brackets):

#+BEGIN_EXAMPLE
                          Store
    ┌──────┬────────────────┼───────────────┬──────────┐
   Dict  [PassThrough]   [Mapping]      [URL-Based]   Disk
            │        ┌──────┼──────┬─────────┐
        ┌───┴────┐ [Relative] [JSON]  [Sequential]
   [Switching*][Logging]
        └─[Cache]
#+END_EXAMPLE
(*Switching actually subclasses DictStore — see its listing.)

** The combinator catalog, with implementations

*** PassThrough — the identity (SC Fig. 11)
#+BEGIN_SRC smalltalk
class PassThrough : Store {
    var source.
    -at:ref                    { self source at:ref. }
    -<void>at:ref put:object   { self source at:ref put:object. }
    -<void>at:ref merge:object { self source at:ref merge:object. }
    -<void>deleteAt:ref        { self source deleteAt:ref. }
}
#+END_SRC
"Source" is defined from the GET point of view (SC footnote 5).
Configuration and use (SC Fig. 12):
#+BEGIN_SRC smalltalk
scheme:p := PassThrough store.
scheme:p setSource:DictStore store.
p:hello := 'world'.
p:hello.
#+END_SRC

*** MappingStore — the abstract map() (SC Fig. 14)

Richer than a Unix filter because the store protocol is bidirectional:
three overridable mappings — the ref going down, data coming up, data
going down.

#+BEGIN_SRC smalltalk
class MappingStore : Store {
    var source.
    -mapRef:ref                  { ref. }
    -mapRetrieved:object ref:ref { object. }
    -mapToStore:object ref:ref   { object. }
    -at:ref {
        var retrieved := (self source at:(self mapRef:ref)).
        self mapRetrieved:retrieved ref:ref.
    }
    -<void>at:ref put:object {
        var toStore := self mapToStore:object ref:ref.
        self source at:(self mapRef:ref) put:toStore.
    }
    -<void>at:ref merge:object {
        var toMerge := self mapToStore:object ref:ref.
        self source at:(self mapRef:ref) merge:toMerge.
    }
    -deleteAt:ref { self source deleteAt:(self mapRef:ref). }
}
#+END_SRC

With identity mappings it degenerates to PassThrough. Mappings are
overridable methods rather than function arguments *by design*: "to
encourage named, reusable components" — the same anti-lambda stance as
the Java Streams critique.

*** RelativeStore — prefix mapping (SC Fig. 15)
#+BEGIN_SRC smalltalk
class RelativeStore : MappingStore {
    var prefix.
    -mapReference:ref { self prefix referenceByAppending: ref. }
}
#+END_SRC
Decouples clients from absolute locations (document directories, service
URLs, test servers). Setup (SC Fig. 16):
#+BEGIN_SRC smalltalk
homeRef := ref:file:{env:HOME}.
scheme:home := RelativeStore storeWithRef:homeRef.
scheme:home setSource: scheme:file.
home:.bashrc            "→ the user's .bashrc"
#+END_SRC

*** Serialiser — data-only mapping (SC §3.1.4)
A MappingStore that maps only data: external serialized form (JSON, XML)
below, object graph above. No listing in the paper; the JSON store in the
diagrams is the canonical instance.

*** SwitchingStore — the mount table (SC Fig. 17)
#+BEGIN_SRC smalltalk
class SwitchingStore : DictStore {
    -storeForRef:ref           { super at: ref firstPathComponent. }
    -at:ref                    { (self storeForRef:ref) at:ref. }
    -<void>at:ref put:object   { (self storeForRef:ref) at:ref put:object. }
    -<void>at:ref merge:object { (self storeForRef:ref) at:ref merge:object. }
    -deleteAt:ref              { (self storeForRef:ref) deleteAt:ref. }
}
#+END_SRC
Routes by first path component, "comparable to a mount point." Note it
*is a* DictStore — the routing table is itself a store.

*** CachingStore — the workhorse (SC Fig. 18)
#+BEGIN_SRC smalltalk
class CachingStore : PassThrough {
    var cache.
    -copyFromSourceToCache:ref {
        var result := super at:ref.
        self cache at:ref put:result.
        result.
    }
    -<void>at:ref {
        var result := self cache at:ref.
        result ifNil: { result := self copyFromSourceToCache:ref. }
        result.
    }
    -<void>at:ref put:object {
        self cache at:ref put:object.
        super at:ref put:object.
    }
    -<void>at:ref merge:object {
        self copyFromSourceToCache:ref.
        var merged := self cache at:ref merge:object.
        self source at:ref put:merged.
    }
    -<void>deleteAt:ref {
        self cache deleteAt:ref.
        super deleteAt:ref.
    }
    -<void>invalidate:ref { self cache deleteAt:ref. }
}
#+END_SRC

Read-through on GET; write-through on PUT; explicit =invalidate:= instead
of automatic invalidation. Read the merge path carefully — it is the
standing RESTLY overclaim correction in the flesh: *refresh the cache
from the authoritative source first*, merge in the cache, then PUT the
merged result to the source. Merge never trusts a possibly-stale cache
entry.

*** LoggingStore + filters — the adapter to the stream world (SC Fig. 19)
#+BEGIN_SRC smalltalk
class LoggingStore : PassThrough {
    var log.
    -<void>at:ref put:object {
        super at:ref put:object.
        self log write:(RESTOperation verb:'PUT' reference:ref).
    }
    -<void>at:ref merge:object {
        super at:ref merge:object.
        self log write:(RESTOperation verb:'MERGE' reference:ref).
    }
    -<void>deleteAt:ref {
        super deleteAt:ref.
        self log write:(RESTOperation verb:'DELETE' reference:ref).
    }
}
#+END_SRC

Passes everything through unchanged; additionally writes a
=RESTOperation= (verb + reference, *no data*) to its log. Only writes are
logged. The log target is anything implementing =-write:= — a *filter*.
This is the single sanctioned junction between the store world and the
stream world (the RESTLY "stores are not streams" ruling cites exactly
this seam). Because notifications carry refs, not pointers, the data need
not even exist in memory (deletions).

Configuration (SC Fig. 20):
#+BEGIN_SRC smalltalk
scheme:p := LoggingStore store.
scheme:p setSource:DictStore store.
scheme:p setLog: stderr.
p:hello := 'world'.        "→ 'PUT hello' on stderr"
#+END_SRC

Two ready-made filters:
- *StoreNotifications* (SC Fig. 21): turns RESTOperations into
  NSNotificationCenter MVC change notifications.
- *Copier* (SC Fig. 22): one-way store synchronization —
  #+BEGIN_SRC smalltalk
  class Copier {
      var source. var target.
      -<void>write:restOperation {
          restOperation verb = 'PUT' ifTrue:{
              var ref := restOperation reference.
              target at:ref put:(source at:ref).
          }
          restOperation verb = 'DELETE' ifTrue:{ target deleteAt:ref. }
      }
  }
  #+END_SRC
  This is the engine of Constraint Connectors: dataflow constraints that
  work over *arbitrary* stores.

*** The asynchronous writer (SC Fig. 31) — composition earns its keep
#+BEGIN_EXAMPLE
 client ──▶ CachingStore ──cache──▶ Memory ◀──source── Copier
                │source(writes)        (reads)            │target
                ▼                                         ▼

#+END_EXAMPLE

Synchronous disk writes throttle the Fig. 30 stack. Fix: replace the
write path with Logger → async Queue → Copier; the Copier pulls the
*current* value from the memory store and pushes it through JSON to disk.
The queue decouples write latency and *coalesces* writes (the copier
always reads the freshest value, so duplicate queued refs collapse).

Two facts worth quoting in any composability argument:
- The first implementation was a single hand-written store — "very
  complex and error-prone." The compositional version was simpler,
  smaller, and *worked out of the box* from pre-tested parts.
- Semantics shift subtly: while writes are outstanding, the cache entry
  *is the source of truth*, not a discardable copy. Composition does not
  absolve you from reasoning about the composite's invariants.

** Evaluation numbers

- *Reliability*: BBC production outages down ~50×  (partial failure
  modes of distribution simply removed — the Waldo argument run in
  reverse). Wunderlist 3.0 crashes down 10× vs 2.x, on a .0 release.
- *Performance* ("hello world" request throughput, SC Fig. 38, log
  scale): Sinatra 938 r/s, Flask 1 523 r/s, Fastify 58 120 r/s, storage
  combinators over HTTP 63 735 r/s, storage combinators *in-process*

  variant. BBC production: ~100× improvement.
- *Productivity*: BBC code size ÷4 while *adding* two output media.
  To-Do developer report: unified layer interface ≈ "infinitely
  extensible" with minimal glue; combinators toggled on/off as feature

  50–60% of the code (parts achieved <50%). Reported downsides, verbatim
  concerns: dataflow paths not determinable before runtime (the object

- *Size*: the Objective-C implementation is <1 KLOC including unit

** Discussion: inverting OO

Kay's Smalltalk was a scaled-*down* network of computers exchanging
messages — but that network was notional. The real planet-scale network
chose REST: names + a small verb set with state-based semantics. REST
demonstrates you can hide state *and computation* behind a
state-oriented interface, inverting the OO doctrine that interfaces must
be procedural. And since storage, not computation, has driven workloads
for a decade+, forcing recursive decomposition along procedural lines is
itself an architectural mismatch. Brooks, 1975: show me your tables and
I won't usually need your flowchart.

Section 7.2 then *names the field* — and immediately bounds it: storage-
oriented composition is powerful, "one should refrain" from crowning it
an all-encompassing ontology like OO. Citing Hughes: modularity is
bounded by the kinds of glue available; we need *many kinds of
connectors*. That sentence is the bridge to the 2024 paper.

** Related-work boundary stakes (each one a RESTLY fence post)

- /Genesis/: composes sub-store-granularity parts into one store; no
  symmetric store-interface composition.
- /Stackable filesystems, FUSE/: kernel-mediated, global, privileged,
  byte-oriented (forces serialisation); combinators are in-process,
  per-program, object-carrying. MPWFoundation ships a FUSE adapter the
  other direction.
- /Plan 9/: per-process hierarchical namespaces over diverse resources —
  closest OS-level relative — but server processes/kernel transitions and
  byte-oriented APIs.
- /HTTP middleware/: in-process, stackable, request-modifying — but tied
  to a specific HTTP server and to HTTP itself. A "rich source of
  inspiration" for future combinators.
- /RInK paper (Adya et al.)/: independent evidence that remote key-value
  stores should move back in-process; combinators keep such designs
  modular.
- /Properties (C#, Objective-C, Eiffel, Swift)/: data-like syntax but no
  full name/operation separation, so no way to capture all names for one
  operation and interpose generic services.
- /Lenses (Foster et al.)/: share bidirectionality, but operate
  per-function; combinators abstract over an *entire identifier set* at
  once. (The RESTLY "not lenses wholesale" ruling is this sentence.)

** The future-work paragraph (the RESTLY charter)

SC §9, in full paraphrase because every clause matters: how to type and
statically check storage combinators is open; the generic nature that
makes them composable makes correct-connection verification hard;
existing generic approaches are "probably insufficient, because even
single instances of the combinators will usually be processing many
different types"; and then the sentence the thesis answers — "One
possibility is that the types move from the operations to the polymorphic
identifiers." RESTLY's =[K, V]=-on-the-store-interface design is the
other announced branch of the same fork: types move onto the *store*
rather than the identifier, with =restly_schemes= recovering Weiher's
monomorphic universal composability at =[STRING, STRING]=.

Also queued as future work: composition-level tracing/debugging by
auto-inserting logging stores (answering the To-Do team's reported
downside), and graphical specification of compositions.

* Part 4 — Beyond Procedure Calls as Component Glue (Onward! '24)

The capstone, and the *normative* paper: wherever earlier papers differ,
this one wins. Subtitle: "Connectors Deserve Metaclass Status" — a
deliberate escalation of Mary Shaw's 1994 "Procedure Calls Are the
Assembly Language of Software Interconnection: Connectors Deserve
First-Class Status."

** Analogy

Shaw asked for connectors to be first-class citizens — values you can
define and pass around. Thirty years of ADLs and ArchJava tried exactly
that and industry ignored them. Weiher's move is subtler: don't add a new
citizen class; *promote the civil service*. Connectors already exist in
every language (calls, variable access); make each of those existing
mechanisms polymorphic behind its familiar syntax, governed by a
metaobject protocol — the same trick CLOS played on method dispatch. The
surface language barely changes; the space of systems it can express
explodes.

** The connector taxonomy (BPC Table 1, from Mehta/Medvidovic/Phadke)

| Connector type | Variants                                        | Objective-S support |
|----------------+-------------------------------------------------+---------------------|
| Procedure call | subroutine, function, method, macro, coroutine… | direct (HOM)        |
| Data access    | local variable, file API, REST APIs…            | direct (PI + SC)    |
| Stream         | Unix pipes, Go channels, TCP sockets…           | direct (PWS)        |
| Event          | notifications, message brokers…                 | direct (protocols)  |
| Distributor    | naming, DNS, X.400…                             | direct (schemes)    |
| Linkage        | compile-time, run-time, dynamic, static         | indirect            |
| Adaptor        | interpreters, DeLine packaging…                 | indirect            |
| Arbitrator     | locks, transactions…                            | (not claimed)       |

Definitions: /architecturally monomorphic/ = at most one variant per
connector type expressible directly (all mainstream languages);
/architecturally polymorphic/ = several-to-all variants of a type behind
one syntax. The strategy: (1) make existing connectors polymorphic;
(2) minimally extend surface syntax for additional types; (3) one generic
connection mechanism; (4) support features (complex object literals).

Objective-S is a Smalltalk generalization implemented on the Objective-C
runtime; full peer to Objective-C, no FFI, methods indistinguishable to
callers.

** Connector type by connector type

*** Naming + data access (PIs + storage combinators, recapped and extended)

#+BEGIN_SRC smalltalk
greeting := 'Hello World!'.
var:greeting := 'Hello World!'.        "same reference — default scheme is var:"
file:hello.txt := greeting.
var:conf/2024/website := https://2024.splashcon.org.
#+END_SRC

Identifiers denote *values*; prepend =ref:= to get the reference itself.
References are created *by stores*, which control the reference kind

corpus for the data-access claim:

| Data store        | Conventional PL                                  | Objective-S        |
|-------------------+--------------------------------------------------+--------------------|
| Local variable    | =hello=                                          | =hello=            |
| Environment var   | =getenv("hello");=                               | =env:hello=        |
| Dictionary        | =dict at:'hello'=                                | =dict:hello=       |
| File              | =f=fopen("hello","r"); fread(buffer,len,f);=     | =file:hello=       |

And uniformity is behavioral, not just syntactic: =file:.=, =env:.= and
=task:.= all produce directory listings in the =st= shell (BPC

environment, and an object's instance variables.

*** Property paths — defining stores declaratively (BPC §2.1.2)

The 2024 replacement for hand-implementing the four Storage methods.
Paths are declared at method level with a leading =/=, may contain
=:parameters= and =*= wildcards (bound as variables in the body), match
in file order, respect inheritance (unmatched paths go to the
superclass), and each path exposes only the REST verbs it mentions. PUT/
POST bodies arrive as =newValue=.

The To-Do store, complete (BPC Listing 3):
#+BEGIN_SRC smalltalk
scheme Todo : MappingStore {
    var tasks.
    -taskList { this:tasks allValues. }
    /tasks {
        get { self tasks. }
    }
    /task/:id {
        get { this:tasks at:id . }
        put { this:tasks at:id put:newValue.  self persist. }
    }
    /complete/:id {
        post { (this:tasks at:id) setDone:true.  self persist. }
    }
    -<void>persist { source:tasks := self tasks. }
}
#+END_SRC

The 2020 paper's SQLite adapter (GT Fig. 19) shows the same construct
computing table metadata from =PRAGMA= queries behind =/schema/:table= —
stores that compute rather than store, declaratively.

*** Streams (Polymorphic Write Streams)

Syntax: =<<= writes to a stream; =^= passes to the next pipeline stage.
Protocol — one message:
#+BEGIN_SRC smalltalk
protocol Streaming {
    -<void>writeObject:anObject;
}
#+END_SRC
Anything implementing it is a target; anything sending it is a source.
Adopters include filters, polymorphic references, one-argument closures,
and mutable arrays. Filter definition compressed to method-weight (BPC
Listing 6):
#+BEGIN_SRC smalltalk
filter add3   |{ ^object + 3. }
filter times4 |{ ^object * 4. }
filter upcase |{ ^object uppercaseString. }
filter dup    |{ ^object. ^object. }        "1-in, 2-out — not a function"
#+END_SRC
Pipelines: =add3 → times4=. Packaging as a real Unix filter (BPC
Listing 21):
#+BEGIN_SRC smalltalk
#!env st
filter upcase |{ ^object uppercaseString. }
(stdin → upcase → rawstdout) run
#+END_SRC
The 2020 paper adds the operational virtue: the construction is passive
and *asynchrony-agnostic* — the same composition works sync or async, no
callbacks, no promise pyramids.

*** Events / implicit invocation

A /notification protocol/ declares the one message subscribers receive:
#+BEGIN_SRC smalltalk
protocol ModelDidChange { -<void>modelDidChange:object; }

protocol:ModelDidChange notify: ref:myObject.     "send"
protocol:ModelDidChange << ref:myObject.          "send, as a stream target"
#+END_SRC
Classes *adopt* the protocol to auto-subscribe. Distributed events reuse
the stream abstraction — RabbitMQ as a component (BPC Listings 34–36):
#+BEGIN_SRC smalltalk
r := #OQRabbit{ queue:'testQueue', sending: true, host:'localhost' }.
r << 'Hello Objective Rabbit'.

text := #TextField{ frame:(180@24) }.  text → queue.     "UI → queue"
queue → stdout.                                          "queue → console"
queue → protocol:ModelDidChange.       "remote observer pattern"
#+END_SRC
The equivalent Python/pika receiver is 52 lines whose destination is
buried in a callback (BPC Listing 37) — the point is not line count but
that the architecture is *invisible* in the procedural version.

*** Procedure calls made polymorphic — Higher Order Messaging

A HOM = prefix message (delivery semantics) + argument message (intent):
#+BEGIN_SRC smalltalk
robot turn: 20.               "default HOM: sync"
robot sync turn: 20.          "fully qualified equivalent"
robot async turn: 20.         "asynchronous"
robot future turn: 20.        "remote/deferred — Croquet-style"
robots do turn: 20.           "multi-receiver"
receiver static msg:arg.      "static dispatch"
receiver inline msg:arg.      "inlining"
#+END_SRC
Conceptually *all* sends are HOM-mediated, with =sync= as default.
Compiler support means HOMs can go both more dynamic *and* more static
than plain messaging — contrast the Cocoa
=performSelectorInBackground:withArgument:= and BeOS BMessage
contortions (BPC Listings 24–25) which abandon the messaging syntax
entirely.

=|== (permanent assignment) = =:== that keeps holding. Built entirely
from the existing pieces — LoggingStore decorates any store, sends update

two-liner via property paths (BPC Listing 39):

}
#+END_SRC

#+BEGIN_SRC smalltalk

*** The polymorphic connection designator =→= (BPC §3)

Terminology is deliberate: a *designator*, not an operator — it does not
command a one-time imperative hookup; it *is* the connection for the
connection's lifetime (a breakpoint on it fires whenever communication
crosses it). The full architecture model behind it (BPC Fig. 2):

#+BEGIN_EXAMPLE
 Component A ─ Port A.1 ─ Role 1 ─[ Connector ]─ Role 2 ─ Port B.1 ─ Component B
#+END_EXAMPLE

A fully qualified connection names all seven elements; almost always you
write only the two components. Matching algorithm: find each component's
default port → ask the ports for the default connector → match ports to
the connector's LHS/RHS roles → send =connect=. Ports can be named via
the =port:= scheme:
#+BEGIN_SRC smalltalk
celsiusField → port:model/setCelsius: .
#+END_SRC
Every message an object responds to is a port by default. The metaobject
protocol defines component/port/connector interfaces; conforming objects
participate in matching — the exact pattern of the Storage protocol,
lifted to connection itself.

#+BEGIN_SRC smalltalk

** Evaluation and the two big surprises

1. /Connectors are few./ The expectation was first-class connector
   definition syntax à la Shaw; Objective-S has it and it goes unused.
   Connector *types* number in the single digits; connectors are far
   fewer than components; but they are used constantly — so the winning
   design is optimized surface syntax per *type* + metaobject-level
   polymorphism per variant, not user-defined connector zoos. Few
   compatible reference interfaces are also exactly what makes glueless
   composition and =→= possible.
2. /Slow language, fast systems./ A tree-walking interpreter serving
   ~89 000 r/s on the tasks backend vs Sinatra's ~1 800 r/s (BPC Fig. 7,
   M1 MacBook), because the language connects fast C/Objective-C
   components "and then gets out of the way," while conventional
   frameworks burn cycles metaprogramming REST into procedures. The
   objective.st site survives Hacker-News-front-page loads on a free-tier
   ARM instance (~1 800 r/s capacity). Corollary honestly stated: with
   more Objective-S in the hot path, throughput falls (fully-interpreted
   hello-server ≈60 K r/s); a young native ARM64 compiler (no LLVM, no
   optimizations, from Wirth's compiler book) already gains 2.6×
   (BPC Fig. 8, Listing 48):

** Related work, 2024 framing

- /Previous own work/: PIs, SCs, PWS, HOM are inputs; the novelty here is
  the coherent MOP organized along software-architectural lines, plus
  =→=. The storage-combinator+stream constraints were declared remote
  "future work" in Constraints as Polymorphic Connectors (2016) — and
  "worked out very naturally."
- /ADLs (ACME, Rapide, UniCon)/: separate representations, verbose (the
  ACME encoding of =ls | wc= is a 14-line System block — BPC Listing 50),
  no implementation help, unused in industry. Objective-S makes the
  architecture *be* the implementation.
- /ArchJava/: the direct predecessor by intent; failed because connectors
  were bolted onto full Java — more cumbersome than the built-ins they
  competed with. Objective-S generalizes instead of extends (the same
  verb Gentle Tyranny applied to call/return).
- /CLOS/AMOP/: the governing inspiration — a metaobject protocol
  describes a *region* of language-design space; Objective-S enlarges the
  region across architectural styles while keeping a navigable
  conceptual model (software architecture itself).
- /CLIC/: component language symbiotic with Smalltalk — but still
  separate, no MOP integration, call/return only.
- /DSLs/: costly, overlapping, rudimentary; the diagnosis is inverted —
  general-purpose languages "are not general enough." Nile/Gezira was
  absorbed as adapted filters rather than reimplemented.
- /Plan 9/: OS-mediated storage unification → serialisation + POSIX
  overhead = packaging mismatch; Objective-S keeps object identity
  in-process and can *export* any scheme as a filesystem (FUSE/WebDAV)
  when files are wanted.

* Coda — The Tao of AOP (twelve points)

A memorization aid, not a substitute for the parts above. Each point is a
compression of an argument made at length in the corpus; the parenthetical
tells you where to go when the compression stops being enough.

1. *The architecture is the connectors, not the boxes.* Components
   compute and store; connectors /are/ the system. A program whose glue
   is invisible is a program whose architecture is invisible.
   (BPC §1, Fig. 1)

2. *Separate the name from the operation.* =setName:= fuses location and
   verb; =PUT name= does not. Only when they are separate can an
   intermediary stand between them. Everything else in the corpus
   follows from this cut. (PI §2.4; SC Table 1)

3. *Few verbs, many names.* Four operations over an open-ended
   identifier space beats infinite operations over closed interfaces.
   Syntactic compatibility by default is what makes composition cheap
   enough to actually happen. (SC §1 — Unix filters and the WWW)

4. *Symmetry is the whole mechanism.* A combinator provides the same
   interface it consumes. Interface-in equals interface-out, therefore
   closed under composition, therefore =A → B → C= is always legal.
   (SC Figs. 9–10)

5. *A store need not store.* It may compute, translate, route, or
   refuse — as long as it answers the four verbs. Behavior hides behind
   state-shaped interfaces just as well as state hides behind
   behavior-shaped ones. This is OO inverted. (SC §3, §7.1)

6. *The program text should be the connection, not set it up.* A binding
   established as a side effect has no line for the debugger to point
   at. Dijkstra's argument against goto, applied to glue: shorten the
   gap between static text and dynamic process. (GT §5.4; BPC §3 —
   designator, not operator)

7. *Computers are filing systems.* Storage and communication replaced
   computation as the dominant workload; a language whose only
   abstraction is "compute and terminate" mismatches most programs
   before the first line is written. (GT §1, §7 — Feynman, Steele,
   Black)

8. *The tyranny is gentle because the simulation is almost good enough.*
   Call/return can imitate any style — streams, events, constraints —
   closely enough that objecting feels like splitting hairs. The
   differences are not small, just subtle. Distrust "almost."
   (GT §9.1 — Java Streams)

9. *Generalize, don't extend and don't replace.* Call/return survives as
   the special case, like Newton inside Einstein. ArchJava extended and
   lost; the ADLs replaced and were ignored. (GT §4; BPC §8.2, §8.4)

10. *Connector types are few; use each constantly.* Single digits of
    types in the wild — so give each type one optimized syntax and push
    variant polymorphism down into the metaobject protocol. First-class
    connector definition syntax exists in Objective-S and goes unused.
    (BPC §7.1)

11. *Scale down, don't distribute.* Fielding's generic-interface
    argument contains nothing that requires a network. Move REST
    in-process and the partial-failure modes vanish while three orders
    of magnitude of throughput appear. (SC §1, §6.1–6.2)

12. *Test with smaller configurations, not mocks.* The production
    parts, arranged more simply, are the test double. Composition that
    cannot be reconfigured for testing was never really composition.
    (SC §5.2, Fig. 33)

* Coda II — The Tao, operationalized (agent directives)

The twelve points of the first coda, restated as concrete engineering
directives with code, followed by the classification procedure and worked
examples. Eiffel snippets are RESTLY-flavored; Objective-S snippets quote
the corpus.

** =<|= vs =→= — Eiffel is left-handed

Weiher's =→= reads *source-to-client* (left-to-right toward the front):
#+BEGIN_SRC smalltalk
ref:file:{env:HOME} -> scheme:file -> SchemeHTTPServer port:8080.
#+END_SRC

RESTLY's =<|= reads *client-to-source* (left-to-right toward the back):
#+BEGIN_SRC eiffel
routes ["/todos"] := (create {GATEWAY}) <| todos_table
#+END_SRC

This is not a cosmetic flip — it aligns the composition direction with
Eiffel's evaluation direction:
1. Eiffel is left-handed: the target of an expression is the leftmost
   entity; =a <| b= means "a, backed by b" — the subject acts.
2. The reader meets the HTTP boundary first: gateway (what the client
   talks to) is leftmost; the backing store is rightmost — same order
   as a request traveling inward.
3. Left-associative chains type-check naturally: =(g <| c) <| t= — each
   =<|= returns =like Current=, so the chain builds from the front,
   which is the typed entry point.
4. Route assignment reads as a sentence:
   =routes ["/articles"] := gate <| store= — "the articles route IS
   a gateway backed by a store."

Both directions are valid; =<|= is the Eiffel-native reading because
Eiffel's dot notation, assignment, and aliasing all put the actor on
the left.

** The twelve directives

*** 1. Draw the arrows before writing the boxes
The composition is the first artifact you write, and it survives as the
top of the program:

"Weiher (SC Fig. 25): source-to-client, one expression"
ref:file:{env:HOME} -> scheme:file -> SchemeHTTPServer port:8080.
#+END_SRC

-- RESTLY (realworld_execution.e): client-to-source, same principle
articles := gate <| articles_table           -- the architecture

    -- the route table IS the architecture diagram

Current ["/articles"] [method_post] := agent guarded.extend      -- guarded

#+BEGIN_SRC java

#+END_SRC

*** 2. Pass the location as a parameter; put the verb in the interface

** The decision procedure

Three questions classify any proposed component:

| Q1: answers the four verbs to clients? | Q2: calls the four verbs on a source? | Verdict                                  |
|----------------------------------------+---------------------------------------+------------------------------------------|
| yes                                    | yes                                   | *combinator*                             |
| yes                                    | no                                    | *leaf store*                             |
| no                                     | writes flow one-way into it           | *filter* (Streaming)                     |
| no                                     | no                                    | plain component — keep it out of the chain |

Refinement for combinators: does it map the /ref/, the /data/, the
/routing/, or the /policy/? That picks the superclass
(Relative / Serialiser / Switching / guard-shaped PassThrough).

** Worked example — "How should AUTH be implemented?"

Wrong framing: "the AUTH component" is three components wearing one name.
Decompose by the procedure.

*a) The gatekeeper* — answers verbs, forwards verbs → *combinator*,
guard-shaped PassThrough:
#+BEGIN_SRC eiffel
class RESTLY_GUARD [K, V]
inherit RESTLY_PASSTHROUGH [K, V]
feature
    item (key: K): V
        require authorized: policy.allows (current_principal, key, Read)
        do Result := source.item (key) end
    force (key: K; v: V)
        require authorized: policy.allows (current_principal, key, Write)
        do source.force (key, v) end
end
#+END_SRC
This is where DbC-encodes-HTTP earns its keep: 401/403 as precondition
violations. Corpus warrant: SC Fig. 34 places "authentication frameworks"
/mid-chain/ in the To-Do hierarchy — auth is an intermediary, not a
base-class feature and not a parameter threaded through every call.

*b) The credential injector* — decorates outbound requests near the HTTP
leaf → *mapping combinator* (maps data-to-store, identity elsewhere).
Corpus warrant: BPC Listing 30, =scheme:s3 source setHeaders: #{...}= —
credentials attached at the rawhttp leaf, invisible above it.

*c) Credential storage* — answers verbs, has no source → *leaf store*.
Corpus warrant: Wunderlist (SC Fig. 32), the keychain leaf, with a
SwitchingStore routing sensitive object types to it. Secrets are just
resources with a different backing store.

So: =guard.backed_by (app_stack)= inbound;
=retry.backed_by (header_injector.backed_by (http_client))= outbound;
=switcher → keychain= for the secrets. Three verdicts, no =AuthService=.

** Worked example — "How does DirectoryStore return subdirectories and files?"

Corpus answer: listing is a GET on the container's ref. =file:.= returns
the directory listing in the st shell (BPC Listing 29), and references
can enumerate their child references (PI §3.2) — that is what makes the
generic miller-column browser and HTTP export work at all.

The typed answer exposes why this cannot live in the core protocol: for
=RESTLY_DIRECTORY [K, V]=, =item("src/main.e")= returns a V, but
=item("src/")= returns /a collection of keys/ — a different type through
the same verb. Weiher's dynamically-typed store doesn't notice; a typed
one must. Hence:
#+BEGIN_SRC eiffel
class RESTLY_DIRECTORY [K, V]
inherit
    RESTLY_PROTOCOL [K, V]   -- item/force/remove on file keys
    RESTLY_LISTABLE [K]      -- children (prefix: K): LIST [K] — keys, not values
#+END_SRC
Listing returns *keys* (child refs), never values — clients GET each
child through the same uniform interface, so intermediaries see every
subsequent access (directive 10). Returning materialized values from a
listing would be the bulk-bypass anti-pattern. The NSBrowser lesson
(SC Figs. 35–37) applies verbatim: per-child access over a
whole-directory reader is quadratic — fixed by inserting the stock
cache, not by widening the interface.

Note the derivation: =RESTLY_LISTABLE [K]= being value-type-agnostic is
not a design taste — listing is the one operation whose result type is
K-shaped in a V-typed store.

** Three more, compressed

- /Serializer — store or filter?/ Both exist in the corpus, and the
  procedure disambiguates: bidirectional at a chain seam (must answer
  GET with deserialized objects) → mapping store; one-directional in a
  pipeline → filter. BPC's JSONConverter is the store built /on top of/
  the converter streams — layering, not contradiction.
- /Validation?/ Guard combinator in front of the source; 422 = contract
  violation on =force=. Never inside the leaf — the leaf must stay
  substitutable with the unvalidated test dict.
- /Change notification / UI refresh?/ Never inside any store.
  LoggingStore overlay + filter (SC Figs. 19–21): refs out, no data,
  observers pull. Putting =notify_observers= in a store body is
  directive 4 violated.
