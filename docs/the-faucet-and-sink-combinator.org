** RESTLY_EWF_HANDLER
Then I tried a handler that I would use the RESPONSE as a sink:

#+BEGIN_QUOTE
WSF_RESPONSE is a sink, not an out-parameter. The distinguishing test is: does the caller read the argument afterwards to obtain the answer? For fill_buffer (a_buf), yes — the argument is a value container the caller inspects. For execute (req, res), no. Nobody reads res to find out what happened. It wraps the gateway's output stream; writing to it puts bytes on a socket. The framework calls you, and after you return there's nothing to collect — the effect already left the building.

So CQS isn't being dodged. execute is a command, it returns nothing, its entire purpose is an observable side effect on the external world. That's a command doing exactly what commands are for. My previous answer was about routing a computed value through an argument to dress a function up as a command. Different animal.

This is Beck's Collecting Parameter, or more precisely an effect handle, and it's inherited wholesale from the Servlet/WSGI/PSGI lineage — doGet(HttpServletRequest, HttpServletResponse) with the names changed. Rack and WAI took the other branch: return the response as a value. Worth knowing which tradition you're standing in, because you're about to pick one.
#+END_QUOTE

*** What are the problems with this approach?
This has less problems, but still things to improve:

**** The Queries: item, items, preflight_ok , etc are registered as: AGENT_HANDLER
I.e. as a function whose return value is later sent with WSF_RESPONSE in [[../library/restly/ewf/restly_routed_execution.e]]
It would be better if all of the methods were just commands in [WSF_REQUEST,WSF_RESPONSE] and the queries be wrapped in such a command.
so that the registration mechanism is the same for both queries and commands.

**** The fact that WSF_RESPONSE is a sink that we "inject" to the commands is un-intuitive
Since he are sending a parameter, but this sink looks like a parameter, that we will use to calculate results.
not as something, we will send values to.

**** This patern doesn't scale.
We have a related problem: ENVELOPE
are things that once we ge a set of values with `` we need to package it inside a json `{list_of_items:[...]}`
for ENVELOPE it would seem kind of weird to implement this "inject" the envelope value,
because after that we would use the value, to `a_command(Enclosing. res.send(ENVELOPE)`

I guess what makes it weird is that `RESTLY_` looks like a pipe but has both push and pull semantics.
pull when it is a QUERY and push when it is a command.

**** What would you improve on this approach.
Hide the queries behind a command that uses WSF_RESPONSE.send and then wire the routes only for commands.

** Another approach the SinkCombinator

As we have discussed we have both push and pull semantics in our pipe.
The idea of the sink combinator would be to create a pipe that is infact two

for queries the combitator would look like:

#+BEGIN_SRC Eiffel
  ewf_handler.reqest_item(WSF_REQUEST)  <| backend.item(element_id) -- items is a query so it returns a value.
#+END_SRC

and for commands
#+BEGIN_SRC Eiffel
  ewf_handler.request_remove(WSF_REQUEST) <| backend.remove(element_id) <| ewf_handler.remove() -- the answer gets written here at the end of the sync.
#+END_SRC

So think sink combinator is a "thing" that in the case of queries sits at the front, to receive the results of the pipeline.
and in the case of commands, sits at the begining and end of the pipeline,
At the end to receive notify that the pipeline of commands has ended.
And at the beginning , to start the pileni.
