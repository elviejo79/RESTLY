* Read this first

This document explains the authorization design for RESTLY twice: once
for humans (each idea gets an Analogy, a Diagram, an Example, a Plain
English summary, and only then a Technical definition), and once for a
coding LLM agent (the last section, with exact classes, rules, and
tests).

Replaces the earlier v2 text. Same design, fewer ten-dollar words.

** Tiny glossary

- /store/ :: anything that answers four questions: give me the thing at
  this key (=item=), is there a thing at this key (=has_key=), put this
  thing at this key (=force= / =extend=), delete the thing at this key
  (=remove=). A hash table is a store. In RESTLY, almost everything is.
  In code, the four questions are /six/ typed features — =item=,
  =has_key=, =extend=, =force=, =put=, =remove= in
  =RESTLY_PROTOCOL [K, V]= — plus optional capability mixins
  (=RESTLY_LISTABLE=, =RESTLY_PATCHABLE=, =RESTLY_POSTABLE=,
  =RESTLY_SEARCHABLE=): a resource /is/ its verb set.
- /combinator/ :: a store that is built on top of another store. It
  answers the four questions to whoever asks, and asks the four
  questions to the store behind it. Because the interface going in is
  the same as the interface coming out, you can stack them like Lego.
- /capability/ :: an object that represents "who you are plus what you
  are allowed to do." Think: a hotel keycard.
- /contract/ :: in Eiffel, a =require= (what must be true before
  calling), an =ensure= (what is guaranteed after), or an =invariant=
  (what is always true about an object).
- /trust boundary/ :: the line between "code and data we control"
  (inside) and "whatever arrives from the internet" (outside).

* The one-paragraph version

When a request arrives, a *translator at the door* turns the token
string into a keycard object, or turns the person away (that's a 401).
From the keycard we build a *personal copy of the data* that contains
only what this person is allowed to see and touch. From then on, there
is no security code anywhere — asking for something you can't have
looks exactly like asking for something that doesn't exist (a 404).
Security isn't a check we run; it's the shape of the world we hand you.

* Idea 1 — Two different jobs: the door and the rooms

** Analogy

A hotel. At the front desk, someone checks your ID and gives you a
keycard. That is *authentication*: turning "who claims to be here" into
"a verified identity object." From then on, nobody in the hotel ever
asks for your ID again. Your keycard opens your room, the gym, and the
pool — and silently does nothing on every other door. That is
*authorization*: not a guard interrogating you at each door, but the
set of doors that open for you.

These are two different jobs done by two different things: the front
desk happens *once, at the entrance*; the keycard works *everywhere,
all the time*.

** Example

=DELETE /articles/42= arrives with =Authorization: Bearer eyJhbGci...=.

1. The codec checks the token's signature and expiry date. Bad or
   missing token → *401*, and nothing else ever runs.
2. Good token → the codec builds a =CAPABILITY= (alice, may read all
   articles, may delete only her own).
3. From that capability we build alice's =AUTH_VIEW= of the articles
   store. Article 42 belongs to bob, so in *alice's view, article 42
   does not exist*. Her =DELETE= gets a *404* — the same 404 she would
   get for article 99999, which really doesn't exist. She cannot even
   find out whether 42 is a real article.

** Plain English

Check identity once at the entrance and turn it into an object. After
that, don't guard the data — *shrink the data*. Each person gets a
store that only contains their stuff. Then no interior code ever needs
an "is this allowed?" if-statement, because forbidden things are simply
not there.

** Technical definition

Authentication is a *codec*: an asymmetric translation stage at the
trust boundary that maps a raw credential to a typed =CAPABILITY=, or
refuses (401). Authorization is a *view*: a combinator conforming to
=RESTLY_PROTOCOL [K, V]= whose key space is exactly the subset of the
backing store this capability permits. The codec is the only stage
where the interface changes shape; the view keeps interface-in equal to
interface-out, so it stacks with every other combinator.

* Idea 2 — Existence is proof

** Analogy

You cannot be standing inside the hotel gym without having passed the
front desk, because the only door to the gym opens with a keycard, and
keycards only come from the front desk. Nobody in the gym checks IDs —
your *being there* is the evidence.

** Diagram

#+begin_src mermaid
flowchart TD
    T["token string<br/>(unverified)"] -->|"only path:<br/>codec.mint"| C["CAPABILITY<br/>(verified identity)"]
    C -->|"only path:<br/>AUTH_VIEW.make<br/>require capability_valid"| V["AUTH_VIEW<br/>(authorized store)"]
    V -->|"item / force / remove"| D["data"]
    X["skip the codec?"] -.->|"impossible:<br/>no other creation<br/>procedure exists"| V

** Example

In Eiffel, =AUTH_VIEW='s only creation procedure is:

#+begin_src eiffel
make (a_cap: CAPABILITY; a_back: RESTLY_PROTOCOL [K, V])
    require
        capability_valid: a_cap.is_valid
#+end_src

There is no way to hold an =AUTH_VIEW= in your hands without someone
having supplied a valid capability. The object's existence *is* the
security check, performed once, at construction.

** Plain English

Instead of writing "check permission" in a hundred places, make it
impossible to build the data-access object without permission. Then the
hundred checks are unnecessary — not skipped, *unnecessary*.

** Technical definition

This is "parse, don't validate" applied to authorization, and it is
also why the design is safe even though Eiffel contracts can be
compiled out in release builds. A =require= that guards a *call* can
vanish; a creation procedure that never ran leaves *no object behind*.
Enforcement lives in construction, not in monitoring. The old v1 term
for this object was =AUTHORIZED_CONTEXT=; in v2 it grew four verbs and
became a store.

In RESTLY terms: =AUTH_VIEW= inherits =RESTLY_COMPOSABLE= (hence
=K -> HASHABLE= in every signature) and must *narrow the export* of
=make_with_back= to ={RESTLY_COMPOSABLE}= in its inherit clause. The
base class leaves it public, which would let any holder re-wire an
existing view to a different backing store with no capability check —
un-proving the existence proof. Narrowed, =<|= still composes (it
calls =make_with_back= from inside the combinator family, and the
=twin= it wires carries the capability, so the invariant holds), but
outside code's only path to a wired view is =make (a_cap, a_back)=.

* Idea 3 — Forbidden looks like absent (the 404 rule)

** Analogy

A Netflix Kids profile. The horror movies are not shown with a padlock
icon saying "you can't watch this" — they *do not appear at all*. As
far as that profile can tell, Netflix simply has no horror movies. The
catalog you see /is/ your permission set.

** Example

#+begin_src eiffel
has_key (a_key: K): BOOLEAN
    ensure then
        visibility_is_authorization:
            Result = (back.has_key (a_key)
                      and capability.permits (a_key, {OPERATION}.read))
#+end_src

Read it aloud: "a key exists in your view exactly when it exists in the
real store AND you may read it." Alice asking about bob's article 42
gets =False= — indistinguishable from asking about an article that was
never written.

** Plain English

If the system answers "that exists but you can't have it," it just
leaked a secret (that it exists). Our default answer is "no such
thing." This isn't an extra privacy feature we bolted on; it falls out
of giving each person a shrunken store.

** Technical definition

v1 had a clause called =no_leak_on_denial= that we admitted was
unenforceable — you cannot realistically write an assertion that
inspects a response body for leaks. v2 dissolves the problem:
=visibility_is_authorization= is an ordinary, monitorable postcondition
on =has_key=. The property moved from "constrain what the response
says" (hopeless) to "constrain what the map contains" (routine).

Sometimes you /want/ to tell the client "this exists but your token
lacks the scope" (HTTP 403, which is friendlier for API developers).
That is a deliberate choice to leak existence, so it must be a visible,
separate component you compose in — =DISCLOSING_GUARD= — used only on
resources whose existence is not itself a secret. Default is 404.

*So the three status codes are three different components:* 401 = the
front desk turned you away. 404 = the door doesn't exist in your hotel.
403 = a door with a window, installed on purpose.

* Idea 4 — The clock is read once (tickets aren't re-checked mid-movie)

** Analogy

Your cinema ticket is checked when you walk in. If the ticket's
validity expires halfway through the film, nobody drags you out of the
theater. Entry time is when tickets matter.

** Example

Alice's token expires at 12:00:00. Her request arrives at 11:59:59 and
takes two seconds to process. It *succeeds*. A request arriving at
12:00:01 gets 401. There is a test that pins exactly this behavior, so
no future "improvement" can quietly change it.

** Plain English

We read the clock once, when the request enters, and use that one
timestamp for every expiry decision in that request. A token can't
"expire out from under" a request that already started — that's not a
bug, it's the documented rule, and it's what every real API gateway
does.

** Technical definition

=authenticated (a_raw, a_time)= and =mint (a_raw, a_time)= take the
time as an explicit argument; the gateway snapshots =clock.now= once at
entry and threads it. This keeps =authenticated= a *pure function* of
its arguments — same inputs, same answer — which is what makes it legal
to use inside contracts (a contract clause that changes value while
you're proving it is worthless). Consequence: =CAPABILITY.is_valid=
deliberately does /not/ include "not yet expired," because an object
invariant must stay true for the object's whole life, and time passing
would silently break it.

For long transactions where this genuinely matters, there is one
sanctioned exception: a transactional store may re-check at *commit* —
like a bar re-checking your card when you close the tab, not while you
drink. =commit require still_granted: capability.is_current (clock.now)=
is a legitimate contract because the code calling =commit= is our own
trusted interior code, which can re-verify first. What is /not/
sanctioned is "check again on the way out" — by then the delete already
happened, and a 401 wrapping a completed action is a lie that invites
the client to retry it.

* Idea 5 — Keep the keycard or reprint it? (lifetimes and revocation)

** Analogy

Two ways to run the hotel. (a) Reprint a fresh keycard at the desk for
every single visit — wasteful-sounding, but cards are cheap, and every
card is guaranteed fresh. (b) Give guests a card at check-in and let
them keep it — faster, but now you need a way to *deactivate* cards
when someone is kicked out. Deactivation is not a new security system;
it's the front desk deleting one row from the card machine.

** Example

#+begin_src eiffel
class SESSION_SWITCH [K -> HASHABLE, V]
        -- remembers: principal → their AUTH_VIEW

    view (a_cap: CAPABILITY): AUTH_VIEW [K, V]
        require
            valid: a_cap.is_valid
        ensure
            bound_to_caller: Result.capability.subject ~ a_cap.subject

    evict (a_subject: PRINCIPAL)
            -- Revoke: this person's authorized world ceases to exist.
        ensure
            gone: not views.has (a_subject)
end
#+end_src

Ban bob → =switch.evict (bob)=. His next request finds no cached view,
goes back through the front desk, and the desk (consulting whatever
made you ban him) refuses.

** Plain English

Per-request views are the simple default: build, use, discard. If
profiling ever shows that's too slow, add a =SESSION_SWITCH= that
caches one view per person — and then "revoke access" becomes one
operation with one obvious name: evict. The famous "JWTs can't be
revoked" problem shrinks to ordinary cache management: how long is your
cache allowed to be stale? Answer: at most until the token's own expiry.

** Technical definition

The switch is a routing combinator memoizing principal → view. Its
staleness window equals the view's lifetime; setting TTL = token =exp=
recovers exactly the stateless-JWT guarantee, and evicting early beats
it. This reframes v1's "revocation breaks purity" fork as standard
cache-coherence engineering rather than a special authorization
problem. (Precedent, for the curious: Plan 9 gave every process its own
namespace, established at mount time — authority /was/ what you could
see. This design is that idea for REST stores.)

* Idea 6 — Same feature, two names (=register= is =extend=)

** Analogy

The same person is "Dr. Ramírez" at the hospital and "mamá" at home.
One human, two names, each right for its context. Nobody thinks the
hospital needs a second, duplicate person.

** Example

#+begin_src eiffel
class USER_STORE
inherit
    RESTLY_PROTOCOL [EMAIL, USER]
        rename
            item as user,
            extend as register,
            remove as deregister,
            has_key as is_registered
        end
end
#+end_src

Domain code reads naturally: =users.register (u, email)=,
=users.is_registered (email)=. Meanwhile every combinator — including
=AUTH_VIEW= — holds the store as =RESTLY_PROTOCOL= and calls =extend=,
landing on the very same feature. One feature, two names, both alive.

** Plain English

The four verbs don't have to make your code read like a hash table.
Eiffel's =rename= lets each class present domain names to humans while
staying a plain store to the machinery. Three rules keep it honest:

1. *Match contracts, not vibes.* "Register" sounds like "save," but
   =force= (overwrite-if-exists) is the wrong verb — registering with a
   taken email must /fail/. The verb whose contract matches is =extend=
   (=require error_409_conflict: not has_key (k)= in
   =RESTLY_PROTOCOL=). Bonus: that precondition /is/ HTTP 409 Conflict,
   and =is_registered= /is/ the email-availability check. (Not to be
   confused with =RESTLY_POSTABLE.extend_new=, which is the opposite
   shape: server-minted key, and a duplicate request is an idempotent
   no-op, not a conflict.)
2. *A verb that won't fit is a store you haven't made yet.* =login=
   fits no verb on users — because it isn't an operation on users. It's
   =extend= on a /sessions/ store. =verify_email= is =remove= on a
   /pending-verifications/ store. When the four verbs refuse an
   operation, they're telling you a resource is missing.
3. *Don't hide a transaction inside a rename.* If =register= also sends
   a welcome email and writes an audit row, it is no longer honestly
   =extend=, and every cache or view stacked on the store is now wrong
   about what a write does. Side effects go in separate composed
   stages; if a renamed feature's =ensure= would need to mention
   anything beyond "the map now has this value at this key," split it
   up first.

** Technical definition

=rename= in Eiffel changes a feature's name in one class's view without
duplicating the feature; contracts, dynamic binding, and the ="[]"=
bracket alias survive. Rule 1 is contract unification (a rename claims
the domain operation and the protocol verb have the same
pre/postcondition shape). Rule 2 is Fielding's resource-modeling
discipline rediscovered from the store side. Rule 3 is frame honesty: a
rename asserts the feature's effects stay within the store's abstract
map. The rename axis and the authorization axis never touch: the view
wraps the protocol type, the rename decorates the domain type, and
=guarded_users.register (u, email)= gets both.

* Costs, plainly

1. /Loggers can't see "who" for free./ The person's identity no longer
   travels with each call; an audit stage must sit behind the view and
   ask it (=view.capability=). Fine, but you must place audit stages
   deliberately.
2. /Write-denial cannot live inside the view's verbs./ In
   =RESTLY_PROTOCOL= every write verb /guarantees success/ by contract:
   =extend=, =force= and =put= all end in
   =ensure error_500_...: has_key (k) and item (k) ~ v=, and =force=
   has no precondition at all. A view that silently refused a write
   would violate its own inherited postcondition — a 500, our bug, not
   the client's. So denial must happen /before/ the call. =AUTH_VIEW=
   provides two one-line queries for exactly this:
   =writable (k: K): BOOLEAN= (=capability.permits (k,
   {OPERATION}.write)=) and =removable (k: K): BOOLEAN= (likewise for
   delete). The gateway asks before calling any write verb and turns
   "no" into a response. Keeping the queries on the view means the
   gateway never touches =CAPABILITY= or =OPERATION= — authorization
   vocabulary stays behind the view's interface. Mind =remove='s trap
   in particular: a key can be read-visible (=has_key= True) yet not
   deletable, so =require has_key= passes and only the =removable=
   pre-check stands between the gateway and a broken
   =error_500_didnt_actually_delete=.
3. /Fresh views cost allocations./ Per request: one small object.
   Ignore until a profiler complains; then add the switch.
4. /Typed permissions multiply types./ =permits= should really know the
   key type (=CAPABILITY [K]=), which means one capability class per
   store family. Probably worth it; still open.

* For the coding LLM agent

You are implementing this design in Eiffel. Everything above is the
/why/; this section is the /what/, in order. The ADEPT sections are the
source of truth for intent; the contracts quoted there are normative.

** Ground rules (violating any of these means you misread the design)

1. Void safety fully on (=void_safety=all= in the ECF). Zero =/= Void=
   assertions anywhere — the compiler already guarantees attachment.
2. There is *no* =HANDLER=, no =AUTHORIZED=, no middleware class, and
   no authorization =require= facing raw input. If you find yourself
   writing a class that takes a request and returns a response, stop —
   everything here is a store (=RESTLY_PROTOCOL [K, V]=) or a codec.
3. The clock is snapshotted once per request and passed as an explicit
   =TIME= argument. Never call =clock.now= inside =authenticated=,
   =mint=, or any contract — except the one sanctioned place:
   transactional =commit= (Idea 4).
4. =CAPABILITY.is_valid= must NOT check expiry (Idea 4, Technical).
5. Denial defaults to absence (404). Do not add "exists but forbidden"
   answers anywhere except the optional =DISCLOSING_GUARD=.
6. Assertion monitoring stays ON in every target. This is a research
   artifact; the contracts are the deliverable. If the flat-short view
   (=eshort=) of a class doesn't read as a specification, the class is
   wrong.
7. Do not mark =authenticated= or =permits= as =once= functions. Pure ≠
   constant.
8. Use =~= (object equality) for =PRINCIPAL= comparison everywhere;
   implement and test =PRINCIPAL.is_equal= first, or every contract
   silently compares references.
9. No capability grants write without read:
   =permits (k, write) implies permits (k, read)=, always. This is what
   makes the inherited /effective/ =force= (which routes on the view's
   own shrunken =has_key=) pick =put= vs =extend= correctly — for any
   permitted write, =view.has_key (k) = back.has_key (k)=, so =force=
   needs no redefinition in =AUTH_VIEW=. A "blind drop-box"
   (write-only) is not a half-permission; per Idea 6 rule 2 it is a
   separate store you haven't made yet. This rule quantifies over all
   keys, so it cannot be a class invariant — it is a stated obligation
   on every =permits= implementation, enforced by construction.
10. The view is the outermost store inside the trust boundary: nothing
    composes between the gateway and the view. Shared stages (audit,
    cache) go /behind/ it, composed with =<|=.

*** M1 — CAPABILITY and AUTH_VIEW

=CAPABILITY= (deferred: =subject=, =is_valid=, =permits (key, op)=) and
=AUTH_VIEW [K -> HASHABLE, V]= (the =RESTLY_COMPOSABLE= constraint)
exactly as in Ideas 2 and 3: creation precondition
=capability_valid=, invariant =capability_valid=, the verbs delegating
to =back= with *no new preconditions* — the inherited
=error_404_not_found: has_key (k)= clause, dynamically bound to the
view's redefined =has_key=, already denies invisible keys (Eiffel
forbids strengthening inherited preconditions; =require else= only
weakens, so a permission clause there would be dead code or a lie).
That the denial comes for free is the design's proof, not a shortcut.
Keep the =visibility_is_authorization= postcondition on =has_key=
verbatim. The view implements the five deferred features of
=RESTLY_PROTOCOL=; the effective =force= is inherited untouched —
ground rule 9 is what makes its routing correct.

Acceptance test (real parts, no mocks): a =RESOURCE_HASH_TABLE= with
rows owned by alice and bob; a simple test capability whose =permits=
allows only alice's rows. Assert: alice's view =has_key= is False for
bob's row; =item= on bob's row is a precondition violation (assert on
the tag =error_404_not_found=); after a denied =remove=, *the row is still in the
backing table* — denial is proven by unchanged state, not by counting
calls.

*** M1b — The view keeps the back's verb set

A view speaking only =RESTLY_PROTOCOL= erases its back's capability
mixins: routing does conformance tests
(=attached {RESTLY_LISTABLE} storage=), so a listable store wrapped in
a bare view answers 405 on list. Worse, an unfiltered listing is
precisely the leak Idea 3 forbids — the catalog you see must /be/ your
permission set. Rules, mixin by mixin:

- =RESTLY_LISTABLE= :: the view's =new_cursor= yields only keys the
  capability permits reading. =wipe_out= keeps its honest meaning:
  =ensure empty: new_cursor.after= empties /your/ world; invisible
  rows survive in the back.
- =RESTLY_SEARCHABLE= :: =search= results filtered by the same rule
  as the cursor.
- =RESTLY_PATCHABLE= :: inherit the default =merge= body — it routes
  through the view's own =item= and =put=, so visibility is enforced
  by dynamic binding, no new code. The gateway treats =merge= as a
  write (=writable= pre-check).
- =RESTLY_POSTABLE= :: the gateway cannot pre-check =writable (k)=,
  because =extend_new= mints the key server-side. The stated rule is
  /ownership-at-birth/: a capability that permits create permits
  write — and, by ground rule 9, read — on keys minted for its own
  principal. =fresh_key= runs behind the view; the minted key is born
  visible to its creator.
- =RESTLY_IDENTIFIABLE= lives on V; =RESTLY_WIRE_SCHEMA= and
  =CALL_RETURN_PROTOCOL= are boundary machinery — none concern the
  view.

Build only the mixin combinations actually used (core
=AUTH_VIEW [K, V]= first, then a listable variant); do not build the
full lattice up front.

Acceptance test: a =RESOURCE_HASH_TABLE= (listable) holding alice's
and bob's rows; alice's cursor yields only her keys; alice's
=wipe_out= leaves bob's rows in the backing table.

*** M2 — JWT wrapping (revised 2026-07-24: the distribution already ships a JWT library)

Obsolete as originally written: there is no =JWT_DECODER= to build.
The distribution's jwt library (=$ISE_LIBRARY/contrib/library/web/authentication/jwt=, already referenced by =restly.ecf= and used by =JWT_AUTH=) does the whole job:
- =JWT_LOADER.token (input, alg, key, ctx)= splits, base64url-decodes, parses claims, and verifies HS256 in one call.
- =JWT_UTILITIES= exposes public =base64url_encode= / =base64url_decode= (the =-_=, unpadded variant the original text feared missing).
- Claims come typed from =JWT_CLAIMSET=: =subjet= (sic), =issuer=, =audience=, =expiration_time=, =not_before_time=, and custom claims via =claim ("scope")=.
Scope is still HS256 only; RS256/ES256 remain out of scope.
The JSON-fallback clause and the RFC 4231 vector requirement are moot: no parser and no HMAC are hand-rolled.

Two traps the library introduces (these concretize ground rule 3):
- =JWT_CONTEXT.time = Void= makes the loader read the current UTC clock itself, silently violating the clock-read-once rule; every context we build must set =time= explicitly to the request snapshot.
- =JWT_CONTEXT.validation_ignored := True= skips signature verification and all claim validation; never touch it.

Acceptance (now certifying our configuration of the library, not code of ours): round-trip test with a hand-built token; tampered-signature test (flip one character → invalid); the RFC 7515 Appendix A.1 example verifies.

*** M3 — JWT_CODEC and JWT_CAPABILITY

=PRINCIPAL_CODEC [C]= (deferred, per Idea 1's Technical definition:
=authenticated (raw, time)=, =mint (raw, time)= with
=require established: authenticated (raw, time)=), then =JWT_CODEC=:
=authenticated= = header present ∧ well-formed ∧ signature valid ∧
=nbf <= time <= exp= ∧ =iss=/=aud= match construction arguments.
(Revised 2026-07-24: the conjunction stays normative, but its implementation collapses to one =JWT_LOADER.token= call with a =JWT_CONTEXT= carrying issuer, audience, and the snapshot time, plus =not has_error=; behavioral rows 1–6 test the semantics.)
=JWT_CAPABILITY=: =sub= → subject, =scope= claim → scopes; =permits=
via scope coverage, with write scope covering read by construction
(ground rule 9); =is_valid= structural only (ground rule 4).

Behavioral acceptance table (each row = one test routine; all use
=TEST_CLOCK= and real stores):

| # | credential | expected |
|---+------------+----------|
| 1 | absent | not authenticated |
| 2 | garbage string | not authenticated |
| 3 | valid claims, wrong key | not authenticated |
| 4 | =exp= < entry time | not authenticated |
| 5 | =nbf= > entry time | not authenticated |
| 6 | wrong =aud= | not authenticated |

* Addendum (2026-07-24) — OPERATION is deleted; a capability is its query set

This addendum amends the sections named below; where they conflict, the
addendum wins.

** The ruling

There is no =OPERATION= class. =CAPABILITY.permits (key, op)= is
replaced by four BOOLEAN queries whose names are the protocol's own
verb vocabulary:

#+begin_src eiffel
readable (k: K): BOOLEAN
writable (k: K): BOOLEAN
        -- writable_implies_readable (ground rule 9)
removable (k: K): BOOLEAN
creatable: BOOLEAN
        -- k-independent: the key does not exist yet
#+end_src

** Why

An operation catalog as a separate enum-like type imports foreign
vocabulary into contracts. The considered alternative — a
=RESTLY_CONSTANTS= class inheriting =RESTLY_PROTOCOL= to keep the
names "inside the protocol" — was rejected as facility inheritance: a
catalog answers no verbs and calls no verbs, so by the decision
procedure it is a plain component that must stay out of the
conformance hierarchy. The lazier fix is to delete the type: the
operation set is not open. Every verb, core or mixin, collapses onto
one of four questions:

| Verb (source)                                | Capability question           |
|----------------------------------------------+-------------------------------|
| =item=, =has_key= (core)                     | =readable (k)=                |
| =new_cursor= (LISTABLE), =search= (SEARCHABLE) | =readable (k)=, per key, by the filter |
| =force=, =put=, =extend= (core), =merge= (PATCHABLE) | =writable (k)=       |
| =remove= (core), =wipe_out= (LISTABLE)       | =removable (k)=               |
| =extend_new= (POSTABLE)                      | =creatable=                   |

Reads are reads whether they arrive one key at a time or through a
cursor. A new question can only appear when a new mixin is written —
so the verb set and the query set grow together: /a resource is its
verb set; a capability is its query set./

** Amendments, section by section

- /Idea 3, Example/ :: the postcondition now reads
  #+begin_src eiffel
  visibility_is_authorization:
      Result = (back.has_key (a_key) and capability.readable (a_key))
  #+end_src
- /Ground rule 9/ :: now reads =writable (k) implies readable (k)=,
  same status (obligation on every implementation, not a class
  invariant). Ownership-at-birth extends it:
  =creatable= implies =writable= and =readable= on keys minted for
  this capability's own principal.
- /Cost #2/ :: =AUTH_VIEW.writable= and =AUTH_VIEW.removable= become
  one-line delegations to the capability's queries of the same name;
  the gateway's pre-check story is unchanged.
- /M0/ :: drop =OPERATION= from the stubs list.
- /M1/ :: =CAPABILITY= is deferred with =subject=, =is_valid=, and the
  four queries above.
- /M1b/ :: the gateway pre-checks =extend_new= with =creatable=. New
  caveat: a key that is readable but not removable makes the view's
  =wipe_out= postcondition (=empty: new_cursor.after=)
  unsatisfiable — the pre-check for =wipe_out= is therefore "every
  visible key is removable," a loop, not a single query.
- /M3/ :: =JWT_CAPABILITY= maps the =scope= claim onto the four
  queries (write scope covering read by construction, per ground
  rule 9).

* Friction log — RESTLY_AUTH v2 (M0–M4)

** What was free

- *Denial for free (the design's central bet — it paid).* =AUTH_VIEW=
  never wrote a single denial precondition. Shrinking =has_key= to
  =back.has_key (k) and capability.readable (k)= made the inherited
  =error_404_not_found: has_key (k)= on =item= / =put= / =remove=
  bind dynamically to the shrunken query. The tag tests prove it: an
  unauthorized =item= fires /the protocol's own/ 404 tag, not an
  auth-specific one. Forbidden ≡ absent fell out of dynamic binding.
- *The addendum's four queries.* Replacing =permits (k, op)= with
  =readable= / =writable= / =removable= / =creatable= deleted
  =OPERATION=, its statics, and all dispatch. Every call site got
  shorter; JWT scope mapping became four one-liners.
- *SESSION_SWITCH.* ~30 lines, compiled and passed first try.
  =HASH_TABLE= + =compare_objects= + =PRINCIPAL.is_equal=-by-name did
  all the work; =bound_to_caller= and =gone= transcribed verbatim
  with nothing to adapt.
- *The distribution JWT library (revised M2).* =JWT_LOADER.token= with
  a =JWT_CONTEXT= carrying the snapshot time validated
  sig+exp+nbf+iss+aud in one call — =authenticated= collapsed to
  three conjuncts. RFC 7515 A.1 vector verified untouched.

** What resisted

- *ECF =extends= does not inherit =<option><assertions/>=* — the
  prime friction. Assertions were silently OFF in the extended
  targets; both tag-violation tests "failed" with
  =DEVELOPER_EXCEPTION= because preconditions never fired at all.
  Ground rule 6 ("assertion monitoring always on") is not one
  setting — it must be re-declared per target. A design that stakes
  denial on live contracts is one ECF omission away from an auth
  bypass that all /behavioral/ tests still pass. The two tag tests
  are therefore load-bearing, not decorative.
- *Capturing the assertion tag.* Three layers deep: unwrap
  =ROUTINE_FAILURE= via =.original=, cast to
  ={PRECONDITION_VIOLATION}=, and read =.description= (=.tag= is the
  generic "Precondition violated."; =.message= is obsolete). Plus the
  rescue/retry pattern needs a retry guard or a failing assert inside
  the retried branch loops forever.
- *Test discovery.* =all_classes= root kills the EQA evaluator; the
  working pattern (=<root class="ANY" feature="default_create"/>=)
  came from ISE's own =net_test=. New test classes need a /clean/
  compile to be discovered — incremental reports 0 tests.
- *One typing seam.* The addendum types the queries =k: K= but
  =CAPABILITY= is non-generic (cost #4 still open) — transcribed as
  =a_key: HASHABLE=, argued and accepted. Also =split= on
  =READABLE_STRING_32= yields =LIST [READABLE_STRING_32]=, not
  =STRING_32= (VJAR).

** Where the design surprised

- *Row 9 was unfalsifiable by accident.* With =is_valid=
  structural-only and the snapshot threaded explicitly, there is /no
  code path/ by which the mid-request wall clock can influence
  anything — the test advances =TEST_CLOCK= and nothing can even
  observe it. The test exists purely as a tripwire against a future
  "improvement."
- *wipe_out's postcondition is a theorem about the capability.* A
  readable-but-not-removable key makes =empty: new_cursor.after=
  unsatisfiable — the contract itself forces the gateway's per-key
  removability pre-check. The addendum caught this before I did.
- *Facility-inheritance temptation.* The rejected
  =RESTLY_CONSTANTS=-inherits-=PROTOCOL= idea shows how cheap Eiffel
  makes the wrong move; the addendum's "a capability is its query set"
  is the same information with no inheritance at all.
